# Full zero-shot incident-triage evaluation

This evaluation extends the [20-incident pilot](zero-shot-study.md) to every evaluation record: 220 validation incidents from 11 authored families, 220 test incidents from 11 disjoint authored families, and 24 challenge incidents in 12 paired interventions across four archetypes. The pilot's 20 records are part of the full validation set, so pilot and validation scores are not independent evidence. The 600 training records were not evaluated here. The original five providers used the frozen typed-decision protocol. GPT-6 Luna was added later through the Fuel iX OpenAI-compatible chat proxy, using the same public incident packet, Northstar policy, and allowed answers in a separate zero-shot prompt with no examples or tools. Its prompt was unchanged across the three full sets after a five-case connection test. The earlier model results and test/challenge labels had already been analyzed before Luna was added, so those sets are no longer pristine model-selection holdouts. The validation and test realizations within each family are correlated; the 220 rows in a split are not 220 independent scenarios.

The original model runs declared an 8,192-token context capacity; Luna declared 32,768. All passed the runner's request-size preflight. Luna requested `gpt-6-luna`, resolved to `gpt-6-luna-2026-09-22`, used `reasoning_effort=none`, and kept chat-prompt SHA-256 `f8af64dfd055f61a168088207256fb78d633fc6acc100754d14c757caa089cb9` across all sets. Jev resolved `jev-latest` to `jev-1.13.0`; Kev used source revision `3e1cd3bb588a388a06827443380befece23e68c7` and `jaredpalmer/kev-4b@139fdd94f1b6a6ad80cc15e08fcb99cac885a101` with `Qwen/Qwen3.5-4B-Base@1001bb4d826a52d1f399e183466143f4da7b741b` through MLX bfloat16 on Apple MPS. Kev, Laya, and CLM are local deployments; Jev and Luna are hosted. “Zero-shot” means no Northstar training examples or model-specific few-shot examples, not that the checkpoints have never been trained on other data.

The challenge pairs probe affected-site priority boundaries, stale domain evidence, irrelevant change timing, and topology-dependent ownership. A pair passes only when all four decisions are accepted on **both** incident variants. Joint accuracy requires all four decisions on a single incident; failures and missing records count as incorrect. Field accuracy credits recorded accepted alternatives. The rules baseline is a benchmark-specific heuristic and is included to show how much of this synthetic task explicit policy code already solves.

## Findings

**The late-added chat LLM is the strongest measured provider on these sets.** Luna got 214/220 validation, 202/220 test, and 23/24 challenge incidents fully correct. It made no priority errors on any of the 464 incidents, including all 31 P1 cases. Across the two 220-case splits it got 416/440 fully correct, versus 400/440 for the rules baseline, 240/440 for Jev, and 233/440 for Kev. In a paired bootstrap over authored families, Luna exceeded Jev by 46.4 percentage points on validation (95% interval 22.3 to 70.5) and 33.6 points on test (12.3 to 56.4). Its gaps over the rules baseline were only 6.4 points (−1.4 to 20.5) and 0.9 points (−21.8 to 26.4); these intervals include zero. The intervals describe this small set of synthetic families, not production performance. Luna's chat prompt and the typed API are different interfaces, and prior inspection of these splits limits any model-selection claim.

**Luna's remaining errors are concentrated in a few families.** Five of its six validation misses were `radio_receiver`; the other was `core_service_discovery`. In each it retained `noc` and said evidence was insufficient where the reference selected a domain. On test, 16 of 18 misses were `radio_neighbor`, where it chose `verify_change` as the next check instead of the radio diagnostic; 10 of those also chose `noc`. The other two test misses were `noc_clear_only` cases with an unsupported `verify_change` next check. On challenge, it passed 11/12 complete pairs, missing only one stale-evidence variant because it chose `verify_change` rather than `gather_evidence`. This is strong benchmark performance with a remaining tendency to over-check changes or abstain on some radio evidence.

**The zero-shot Laya and CLM weakness persists beyond the 20-case pilot.** Laya got only 1/220 validation and 4/220 test incidents fully correct; CLM got 0/220 on both. Both answered `insufficient_evidence=yes` on every validation, test, and challenge incident, although the reference is `yes` for only 40/220 in each main split and 6/24 challenge incidents. On validation their median `yes` probabilities were 0.961 and 0.918 respectively. CLM selected `transport` as owner and `gather_evidence` as next check on every validation and test record, even while its distributions and fresh encoder-token usage varied. These are completed model responses, not API failures. The result applies to the pinned local checkpoints and serving paths under this protocol; CLM's Mac path has not been proven numerically equivalent to the upstream vLLM deployment. Severe-priority misses make both models unsuitable for unattended decisions in this benchmark: Laya missed all 31 P1 incidents across the three evaluation sets, and CLM missed 30/31.

**Jev and Kev trade places across disjoint families.** Jev led Kev 112 to 77 on validation; Kev led Jev 156 to 128 on test. Across those two equally weighted synthetic splits, Jev was 240/440 and Kev 233/440, a small aggregate gap that hides large family effects. A paired bootstrap resampling authored families gives Jev minus Kev joint accuracy of +15.9 percentage points on validation (95% interval −11.8 to +45.9) and −12.7 points on test (−33.2 to +2.3). Both intervals include zero. These are descriptive intervals over the observed families, not estimates of production accuracy or a proof that the models are equivalent. Jev changed at least one prediction on 2 of the original 20 pilot cases when rerun at the same resolved `jev-1.13.0` version, although its 11/20 joint pilot score was unchanged; Kev and Laya repeated their pilot choices exactly.

**The bottleneck differs by model and split.** Jev got every P1, P2, and P4 priority correct on both main splits, but called 88/120 validation P3 cases and 92/134 test P3 cases P2. Kev made the same P3-to-P2 error 17 and 11 times. On validation, Kev's owner accuracy nearly matched Jev's (183 versus 185), but owner **and** next check were both correct on only 95/220 cases versus Jev's 160/220. Kev chose `gather_evidence` on 125 validation cases where only 20 references called for it, and `verify_change` on 20 others. It found all 40 reference evidence-insufficient cases but produced 70 false positive flags among the 180 sufficient-evidence cases. On test, both Jev and Kev got owner right on 220/220 and next check on 200/220, while Kev's stronger priority decisions drove its higher joint score. Kev still flagged 48/180 sufficient-evidence test cases as insufficient. A threshold change chosen after seeing these held-out results would be a new tuned experiment, not this zero-shot result.

**Paired interventions expose remaining fragility.** Luna passed all three priority-boundary, irrelevant-change-timing, and topology-change pairs, and two of three stale-evidence pairs. Jev and Kev each passed all three priority-boundary pairs and all three stale-evidence pairs, but neither passed any of the three irrelevant-change-timing pairs or the three topology-change pairs. Both changed their predictions on all three irrelevant-text pairs, where the reference decision should remain invariant. The rules baseline passed 9/12 pairs; its three failures were all topology-change pairs. This is stricter than scoring the 24 challenge rows independently and pinpoints specific decision instability.

**The rules baseline remains a demanding reference on this synthetic policy.** It reached 200/220 on each main split and 21/24 on challenge. Its 20 validation errors all came from `radio_receiver`; its 20 test errors all came from `transport_qos`. Thus even its high aggregate score is template-sensitive. The benchmark was authored with explicit structured priority rules and repeated incident templates, so neither its strength nor Luna's lead establishes production readiness. As a separate offline diagnostic, replacing only model-predicted priority with the exact stated policy rule would raise Jev's joint score to 160/220 validation and 200/220 test, versus 82/220 and 164/220 for Kev. These are **hybrid diagnostics**, not new zero-shot model scores; priority rules cannot repair wrong owner or next-check choices. Luna already got every priority correct, so that diagnostic would not change its scores.

## Latency and interpretation

The test-set successful-call p95 latency was 0.21 seconds for hosted Jev, 5.21 seconds for Luna through Fuel iX, 2.70 seconds for local Kev, 0.47 seconds for local Laya, and 11.74 seconds for local CLM. These are serial, end-to-end timings on different deployments and are not a controlled throughput comparison. Luna's test output combines one partial batch with paced single-incident jobs; per-request latency excludes the pacing delay, and its composite wall time is not comparable to a continuous run. CLM's validation run reused cached embeddings on 156/220 records from an earlier interrupted run; its test run reused 5/220, and its challenge run reused none. The cached responses still count for accuracy, but validation latency is especially unsuitable as an inference-speed estimate.

Fuel iX reported **458,724 prompt tokens and 77,052 completion tokens** across Luna's 464 scored incidents, including 61,483 tokens marked as reasoning despite the requested `reasoning_effort=none`. At [OpenAI's direct standard list rates for GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna), those prompt and completion totals would cost about **$0.084** before any caching or gateway-specific pricing. This is an illustration, not a Fuel iX invoice. The other providers' monetary costs are not estimated, and Luna returned categorical answers without calibrated probabilities.
